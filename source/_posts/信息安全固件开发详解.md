随着智能网联汽车普及，ECU 固件安全成为汽车电子领域的关键能力。**信息安全固件开发**（Security Firmware）涉及安全启动、代码签名、加解密、防篡改、安全升级（OTA）等核心技术。本文系统梳理固件安全开发的知识框架，从威胁模型到实现细节，覆盖嵌入式与汽车电子双重视角。

# 一、为什么要做固件安全

## 1.1 面临的威胁

| 攻击类型 | 攻击手段 | 后果 |
|---|---|---|
| **固件逆向** | 读 Flash、JTAG/SWD 调试口 | 窃取算法与密钥 |
| **固件篡改** | 修改代码、注入恶意逻辑 | 车辆被远程控制 |
| **代码重放** | 回滚到旧版本固件 | 绕过安全补丁 |
| **总线攻击** | CAN 注入伪造报文 | 欺骗 ECU 执行危险操作 |
| **侧信道攻击** | 功耗/电磁分析、故障注入 | 窃取密钥 |
| **供应链攻击** | 恶意代码进入开发流程 | 后门潜伏 |

## 1.2 法规驱动（2024+ 强制要求）

- **UN R155**（联合国法规）：网络安全管理系统（CSMS）——整车量产强制
- **UN R156**：软件更新管理系统（SUMS）——OTA 强监管
- **ISO/SAE 21434**：汽车网络安全工程标准
- 中国《汽车整车信息安全技术要求》等强制性国标

> R155 要求车辆**从开发到退役全程**管理网络安全，直接推动信息安全固件成为刚需岗位。

# 二、安全固件设计核心要素

## 2.1 安全目标（CIA + 额外）

| 目标 | 英文 | 说明 |
|---|---|---|
| 机密性 | Confidentiality | 数据/密钥不泄露 |
| 完整性 | Integrity | 数据/代码不被篡改 |
| 可用性 | Availability | 系统持续可用 |
| 真实性 | Authenticity | 来源可信 |
| 不可抵赖 | Non-repudiation | 操作可追溯 |

## 2.2 安全启动（Secure Boot）

**信任根（RoT）** 链式验证，从最底层建立信任：

```
BootROM ──验证──▶ SPL/BL1 ──验证──▶ U-Boot/二阶段 ──验证──▶ OS/应用固件
  (不可变)         (阶段一)            (阶段二)          (最终系统)
```

每级验证下一级的签名，任何一级被篡改都无法启动。

### 启动验证方式对比

| 方式 | 原理 | 强度 |
|---|---|---|
| **CRC 校验** | 校验和检查 | 低（可被同步修改） |
| **Hash 比对** | 与固定哈希比较 | 中（哈希本身需保护） |
| **数字签名验证** | 用公钥验证私钥签名 | 高（私钥不在设备中） |
| **加密启动** | 固件加密存储，运行前解密 | 高 + 防逆向 |

```c
// 安全启动核心流程（伪代码）
if (verify_signature(fw_bin, fw_sig, pubkey) == OK) {
    boot_into(fw_bin);          // 签名有效才启动
} else {
    enter_recovery_mode();      // 失败进入恢复模式
}
```

## 2.3 硬件信任根

真正可信的根必须在**硬件**中（软件自身无法验证自己）：

| 硬件 | 作用 |
|---|---|
| **eFuse / OTP** | 一次性可编程，存根密钥 |
| **HSM**（硬件安全模块） | 独立安全核，密钥不出硬件 |
| **TEE**（可信执行环境） | ARM TrustZone、RISC-V PMP |
| **Secure Element** | 独立安全芯片（车规 TPM） |

# 三、密码学基础

## 3.1 对称加密

同一把密钥加解密，速度快，用于**数据加密**：

| 算法 | 分组 | 密钥长度 | 说明 |
|---|---|---|---|
| AES | 128 bit | 128/192/256 | 车规标准（AES-128 最常用） |
| SM4 | 128 bit | 128 | 中国国密算法 |

### 工作模式

| 模式 | 特点 |
|---|---|
| ECB | 相同明文→相同密文（不安全） |
| CBC | 引入 IV，块间链接 |
| CTR | 流式，可并行，无填充问题 |
| GCM | 认证加密（加密+MAC 一体，推荐） |

## 3.2 非对称加密

公钥加密/验证，私钥签名/解密，用于**身份认证**：

| 算法 | 特点 |
|---|---|
| RSA | 经典，1024 位已被攻破，需 2048+ |
| ECC | 同强度密钥更短（256 位 ECC ≈ 3072 位 RSA） |
| SM2 | 国密椭圆曲线算法 |

> 实际系统通常**混合使用**：非对称协商/认证密钥，对称加密大数据。

## 3.3 哈希算法

单向散列，用于**完整性校验**：

| 算法 | 摘要长度 | 状态 |
|---|---|---|
| MD5 | 128 bit | 已攻破，禁用 |
| SHA-1 | 160 bit | 已攻破，禁用 |
| SHA-256 | 256 bit | 车规推荐 |
| SM3 | 256 bit | 国密标准 |

## 3.4 消息认证码（MAC）

保证**完整 + 认证**（防伪造）：

- **HMAC**：基于哈希（HMAC-SHA256）
- **CMAC**：基于分组密码（AES-CMAC）
- **MAC** 与 **Hash** 的区别：MAC 需要密钥，无密钥无法伪造

# 四、汽车电子信息安全实现

## 4.1 AUTOSAR 信息安全模块

| 模块 | 功能 |
|---|---|
| **SecOC** | 通信消息认证（防总线伪造） |
| **Csm** | 加密服务管理（统一密码学 API） |
| **Crypto Driver** | 硬件/软件密码驱动（MCAL 层） |
| **KeyM** | 密钥管理 |
| **Eve** | 事件数据记录 |

### Csm API 标准接口

```c
Csm_SignatureGeneration(streamId, data, dataLen, sig, sigLen);
Csm_SignatureVerification(streamId, data, dataLen, sig, sigLen);
Csm_Encrypt(streamId, plain, plainLen, cipher, cipherLen);
Csm_MacGenerate(streamId, data, dataLen, mac, macLen);
```

## 4.2 SecOC：安全车载通信

SecOC（Secure On-board Communication）解决 **CAN 总线消息伪造/重放**：

### 核心机制

1. **MAC 附加**：发送方对 PDU 计算认证码，附加在报文中
2. **Freshness 值（新鲜度）**：防重放，基于计数器/时间戳
3. **密钥管理**：认证密钥定期轮换

```
标准报文 ┌────────────────────────────┐
发送端：  │ PDU 数据 │ Freshness │ MAC │  ← 计算并附加
接收端：  │ 校验 Freshness 在窗口内 │ 验证 MAC │
```

### SecOC 在通信栈的位置

```
SWC → RTE → Com → PduR → SecOC → CanIf → Can → 总线
                      ↑
                 加解密/认证
```

### 两种集成方式

| 方式 | 位置 | 特点 |
|---|---|---|
| **Transparent** | 在 PduR 与 CanIf 之间 | 对上层透明，PDU 级认证 |
| **Non-transparent** | 在 Com 与 PduR 之间 | 信号级，可只保护关键信号 |

```c
// SecOC 配置关键参数
SecOC freshness_value_length = 4;      // 新鲜度 4 字节
SecOC mac_length             = 4;      // MAC 截断 4 字节（可配置）
SecOC authentication_key     = 0x...;  // 认证密钥
SecOC fresh_verify_threshold = 1;      // 窗口内允许偏差
```

## 4.3 HSM（硬件安全模块）

车规 MCU 的独立安全处理器：

| 特性 | 说明 |
|---|---|
| **独立内核** | 自带 CPU（如 ARM SecurCore）、SRAM、ROM |
| **密钥安全** | 密钥存于 HSM 内部，主机无法直接读取 |
| **硬件加速** | AES/ECC/HASH 硬件引擎 |
| **安全启动** | 与主机 BootROM 协同验证 |
| **真随机数** | TRNG 物理熵源 |

典型实现：英飞凌 SHE 规范、Autosar Crypto Stack。

# 五、安全固件开发实战

## 5.1 安全 OTA 升级流程

```
① 云端签名  ──▶  ② 加密固件下发  ──▶  ③ ECU 验签解密  ──▶  ④ 双区切换  ──▶  ⑤ 回滚保护
（私钥签名）    （公钥分发）        （HSM 内完成）      （A/B 分区）      （版本/回滚计数）
```

### A/B 分区双区升级（防变砖）

```
Flash:
┌──────────────┐
│ Slot A（当前）│ ← 运行中
├──────────────┤
│ Slot B（备份）│ ← 写入新固件
├──────────────┤
│ 元数据区     │ ← 启动标志、版本、回滚计数
└──────────────┘
```

## 5.2 固件签名与加密工具链

```bash
# 生成密钥对
openssl ecparam -name prime256v1 -genkey -out key.pem
openssl ec -in key.pem -pubout -out pub.pem

# 签名固件
openssl dgst -sha256 -sign key.pem -out fw.sig fw.bin

# 加密固件（AES-256-GCM）
openssl enc -aes-256-gcm -K $key -iv $iv -in fw.bin -out fw.enc
```

## 5.3 密钥管理

| 阶段 | 密钥 | 存放 |
|---|---|---|
| 开发 | 开发密钥 | 本地/服务器 |
| 量产 | 主密钥/证书 | HSM、HSM 的 HSM |
| 运行 | 会话密钥/认证密钥 | HSM 内部 |
| 下线 | 撤销/销毁 | 证书吊销 |

> 密钥分级 + 最小权限：**永远不要把量产私钥放在开发者电脑上**。

## 5.4 固件安全开发 Checklist

- [ ] 关闭调试口（JTAG/SWD），或加密码保护
- [ ] 使能安全启动（签名链验证）
- [ ] 密钥存储在 HSM/eFuse，而非 Flash 明文
- [ ] Flash 区读保护、写保护、防擦除保护
- [ ] 启动失败进入安全恢复模式（防变砖）
- [ ] OTA 强制验签 + 版本回滚防护
- [ ] 内存保护（MPU/TrustZone）隔离安全与非安全代码
- [ ] 随机数来自 TRNG，不用伪随机
- [ ] 敏感数据内存用后清零
- [ ] 侧信道防护（AES 掩码/乱序，常数时间比较）

# 六、硬件安全机制

## 6.1 ARM TrustZone

将 SoC 分为**安全世界**与**普通世界**，硬件强制隔离：

```
┌────────────────────────────┐
│ 普通世界 (NS)               │
│  OS / 应用                  │  ← 攻击面
├────────────────────────────┤
│ 安全世界 (S)                │
│ 安全固件 / 密钥 / 安全服务  │  ← 受保护
├────────────────────────────┤
│ TZASC / TZPC 硬件控制       │
└────────────────────────────┘
```

- 通过 **SMC 指令** 从普通世界切换到安全世界
- **TZASC** 控制内存区域访问权限
- 安全启动运行在安全世界，验证普通世界的 OS

## 6.2 内存保护

- **MPU**（Memory Protection Unit）：Cortex-M 内存分区权限
- **MMU**（Memory Management Unit）：Cortex-A 虚拟地址隔离
- **MPU 配置示例**：

```c
MPU->RNR = 0;                    // 区域 0
MPU->RBAR = 0x10000000;          // 起始地址（Flash）
MPU->RASR = (0x1 << 28)          // 0x10000000 区域
          | (0x2 << 24)          // 全权限：可读可写可执行
          | (0x1 << 18)          // 区域使能
          | (31 - 0)             // 大小：2GB
          | (0x1 << 1)           // 可执行
          | (0x1 << 0);          // 使能
```

## 6.3 Flash 保护

- **RDP**（Read-out Protection，读保护）等级：0 无保护 / 1 禁止调试读 / 2 永久保护
- **WRP**（Write Protection）：禁止写特定扇区
- **PCROP**（Proprietary Code Read-out Protection）：专有代码读保护

# 七、常见攻击与防御

## 7.1 攻击面与防御手段

| 攻击 | 防御 |
|---|---|
| **调试口攻击** | 关闭/锁定 JTAG、密码保护 |
| **总线嗅探** | 通信加密 + SecOC 认证 |
| **消息注入/伪造** | SecOC MAC 验证 |
| **重放攻击** | Freshness 值 + 窗口校验 |
| **固件提取** | Flash RDP、HSM 密钥保护 |
| **故障注入** | 电压/时钟监测、校验冗余、安全状态机 |
| **侧信道（功耗分析）** | AES 掩码、常数时间算法、HSM 隔离 |
| **降级攻击** | 回滚计数器、版本号防降级 |

## 7.2 常见漏洞示例

```c
// ❌ 危险：常数时间比较
if (memcmp(stored_hash, recv_hash, len) == 0) { ... }
// memcmp 字节顺序返回，攻击者可通过时序差异逐字节猜测

// ✅ 安全：常数时间比较
uint8_t diff = 0;
for (int i = 0; i < len; i++)
    diff |= stored_hash[i] ^ recv_hash[i];
if (diff == 0) { ... }
```

## 7.3 安全开发规范

- **MISRA C** 汽车编码规范（安全子集）
- **CERT C** 安全编码标准
- **代码审计**：静态分析（Coverity、Klocwork、SonarQube）
- **模糊测试**：协议层 Fuzzing（CAN/UDS/OTA 接口）
- **渗透测试**：安全评估流程（根据 ISO 21434 的 TARA 评估）

# 八、ISO/SAE 21434 工程实践

## 8.1 TARA 风险评估

TARA（Threat Analysis and Risk Assessment）是 21434 的核心：

```
资产识别 → 危害场景 → 影响评级 → 攻击可行性 → 风险等级 → 安全目标 → 安全需求
```

## 8.2 安全开发生命周期

```
安全需求 → 安全设计 → 安全实现 → 安全测试 → 安全运维
   ↑         ↑          ↑         ↑         ↑
 定义保护    威胁建模    安全编码   渗透测试   漏洞管理
 目标        TARA      静态分析   模糊测试   CVEs 响应
```

## 8.3 与 ISO 26262 的关系

| | ISO 26262 | ISO/SAE 21434 |
|---|---|---|
| 关注点 | 功能安全（意外故障） | 网络安全（恶意攻击） |
| 目标 | 避免系统失效 | 避免被入侵/篡改 |
| 共同点 | 全生命周期管理、V 模型、风险管理 |

> 功能安全与网络安全互为支撑：安全机制（SecOC 等）本身也要做功能安全分析（FMEDA）。

# 总结

信息安全固件开发的知识主线：

> **威胁模型（为什么要做）→ 安全启动（信任链）→ 密码学（加密/签名/哈希/MAC）→ 硬件信任根（HSM/TrustZone/Flash 保护）→ 安全通信（SecOC）→ 安全升级（签名 OTA/回滚保护）→ 工程规范（ISO 21434/TARA）**

核心思想：**信任必须根植于硬件，验证必须依赖密码学，设计必须贯穿全生命周期**。

> **一句话记住**：信息安全固件 = "让代码只按你的意图运行"——用安全启动保证不被篡改，用 SecOC 保证不被欺骗，用 HSM 保证密钥不被窃取，用 OTA 防护保证不被降级。
