Bootloader（引导加载程序）是嵌入式系统上电后最先运行的程序，负责初始化硬件、加载并启动应用固件。FOTA（Firmware Over-The-Air）则是通过无线网络远程升级固件的能力，是智能网联汽车的"标配"。两者结合，构成了汽车 ECU 软件升级的基础设施。本文从 Bootloader 原理讲到 FOTA 全流程设计。

# 一、Bootloader 是什么

## 1.1 定义与职责

Bootloader 是固化在 MCU 中、上电后第一个执行的程序（运行在 Flash 的固定地址，通常是 0x00000000 或独立扇区）。核心职责：

1. **硬件初始化**：时钟、内存、外设基础配置
2. **启动决策**：决定进入**应用模式**还是**编程模式**
3. **程序跳转**：把控制权交给应用固件
4. **固件升级**：接收新固件、写入 Flash（编程模式）

## 1.2 为什么需要 Bootloader

| 原因 | 说明 |
|---|---|
| **现场升级** | 不拆 ECU 即可更新软件 |
| **FOTA 基础** | 无线升级的本地执行端 |
| **防变砖** | 应用损坏时 Bootloader 仍可恢复 |
| **产线烧录** | 生产线上通过 Bootloader 烧录应用 |

## 1.3 运行模式

```
上电/复位
    │
    ▼
┌─────────┐    条件判定     ┌─────────┐
│Bootloader│ ─────────────▶│ 应用固件 │
│(启动模式)│   跳转条件      │(应用模式)│
└─────────┘                └─────────┘
    │
    │ 升级请求
    ▼
┌─────────┐
│Bootloader│
│(编程模式)│ ← 接收固件、擦写 Flash
└─────────┘
```

**跳转条件**（由编程标志/校验决定）：
- 应用区有效（CRC/签名校验通过）→ 跳转应用
- 应用区无效 → 进入编程模式
- 收到升级请求标志 → 进入编程模式

# 二、Flash 存储布局

## 2.1 典型分区

```
0x00000000 ┌────────────────────┐
           │  Bootloader        │  ← 固定地址，不受升级影响
           ├────────────────────┤
           │  向量表重映射区    │
           ├────────────────────┤
           │  Application A     │  ← 运行中的应用
           ├────────────────────┤
           │  Application B     │  ← 备份/新固件
           ├────────────────────┤
           │  参数区（校准数据）│
           ├────────────────────┤
           │  升级标志区        │
           └────────────────────┘
```

## 2.2 双区（A/B）架构

| 特性 | 单区 | 双区（A/B） |
|---|---|---|
| 升级安全 | 升级中断可能变砖 | 中断可回滚 |
| Flash 占用 | 1 倍固件 | 2 倍固件 |
| 升级速度 | 就地升级 | 后台写入+切换 |
| 典型场景 | 产线/售后工具 | **FOTA 必备** |

### A/B 切换流程

```
① 从 A 区运行
② 新固件下载到 B 区（后台，不中断运行）
③ 校验 B 区（签名/CRC）
④ 设置启动标志指向 B
⑤ 复位，Bootloader 从 B 启动
⑥ 若 B 启动失败，回滚 A
```

## 2.3 向量表重映射

应用运行后需要重映射中断向量表，否则中断会跳回 Bootloader：

```c
// Cortex-M：SCB->VTOR 指向应用向量表
SCB->VTOR = APP_START_ADDR;   // 如 0x08008000
```

**链接脚本关键点**：应用固件编译时必须用偏移地址

```ld
FLASH (rx) : ORIGIN = 0x08008000, LENGTH = 60K
```

# 三、Bootloader 启动流程详解

## 3.1 启动判定逻辑

```c
void main(void) {
    init_clock();
    init_uart();          // 升级通信接口
    init_flash();

    uint32_t flag = read_boot_flag();

    // 1. 检查升级请求
    if (flag == REQ_UPDATE) {
        enter_update_mode();     // 进入编程模式
    }

    // 2. 校验应用固件
    if (verify_app_fw() == OK) {
        jump_to_app();           // 跳转应用
    } else {
        enter_update_mode();     // 应用无效，等待升级
    }
}
```

## 3.2 跳转应用函数

```c
void jump_to_app(void) {
    // 应用向量表首元素是初始栈顶地址
    uint32_t app_sp = *(volatile uint32_t *)APP_START_ADDR;
    // 第二个元素是复位向量
    uint32_t app_pc = *(volatile uint32_t *)(APP_START_ADDR + 4);

    // 设置新的栈顶
    __set_MSP(app_sp);
    // 跳转到应用复位处理
    void (*reset_handler)(void) = (void (*)(void))app_pc;
    reset_handler();
}
```

## 3.3 升级流程（CAN/串口通道为例）

```
① 上位机发送握手请求（进入编程模式）
② 擦除目标 Flash 扇区
③ 上位机分包发送固件（带序列号+校验）
④ 每包校验，出错重发
⑤ 全部接收后整体 CRC/签名校验
⑥ 设置应用有效标志
⑦ 复位跳转新应用
```

# 四、升级通信协议

## 4.1 自定义协议 vs 标准协议

| 方式 | 优点 | 缺点 |
|---|---|---|
| **自定义简单协议** | 简单、可控 | 不可复用、难测试 |
| **ISO 15765 / UDS 诊断** | 标准化、工具支持 | 帧格式较复杂 |
| **XMODEM/YMODEM** | 简单成熟 | 无安全校验、无断点续传 |

> 汽车 ECU 升级普遍基于 **UDS 诊断协议**（0x34/0x36/0x37 服务），见《UDS诊断协议详解》。

## 4.2 分包与校验

```c
// 升级帧格式示例
typedef struct {
    uint8_t  cmd;        // 命令：0x01 写数据 0x02 校验
    uint16_t seq;        // 包序号
    uint16_t len;        // 数据长度
    uint8_t  data[MAX];  // 固件数据
    uint16_t crc;        // CRC16 校验
} UpgradeFrame;
```

- **分包大小**：受 Flash 页大小、RAM 缓冲、通信速率共同限制
- **CRC**：每包 CRC16 + 整包 CRC32 双重校验
- **断点续传**：记录已写入位置，重连后继续

# 五、FOTA 全流程

## 5.1 FOTA 系统架构

```
┌────────────┐      ┌────────────┐      ┌─────────────┐
│  云端平台  │      │   车机端    │      │  ECU（目标）│
│ 固件仓库    │ ←──▶│ OTA 客户端  │ ←──▶│  Bootloader │
│ 签名/加密   │ HTTP │ 下载/校验   │ CAN  │  写入 Flash │
└────────────┘      └────────────┘      └─────────────┘
```

## 5.2 FOTA 升级时序

```
① 云端下发升级通知（版本/大小/校验值）
② 车机端下载固件包（后台，可断点续传）
③ 完整性校验（哈希）
④ 解密 + 验签（密钥在 HSM 中）
⑤ 通过 CAN/UDS 将固件传给目标 ECU
⑥ ECU Bootloader 擦写 Flash
⑦ 激活新版本并自检
⑧ 上报升级结果，云端记录
```

## 5.3 安全 FOTA 要点

| 环节 | 安全措施 |
|---|---|
| 传输 | HTTPS / TLS 加密通道 |
| 固件 | 数字签名（防篡改）+ 加密（防逆向） |
| 版本 | 版本号 + 回滚计数（防降级攻击） |
| 校验 | 下载后 Hash 校验 + 写入后 CRC 校验 |
| 回滚 | A/B 双区 + 启动失败自动回滚 |
| 认证 | 云端与 ECU 双向认证 |

## 5.4 FOTA 与诊断模式

```
正常模式：应用固件运行，OTA 客户端在后台工作
▼
进入扩展诊断模式（0x10 03）
▼
Bootloader 编程会话（0x10 02）
▼
执行 0x34(请求下载) / 0x36(传输数据) / 0x37(退出传输)
▼
0x11(ECU 复位) 重启进入新固件
```

# 六、Bootloader 开发要点

## 6.1 内存边界与保护

- Bootloader 区设为**只读/写保护**，防止应用误写
- 分区地址用编译期常量，杜绝硬编码混乱
- Flash 擦写期间**关中断**，防止中断向量跳转冲突

## 6.2 通信接口选择

| 接口 | 速率 | 适用 |
|---|---|---|
| UART | 慢 | 产线、调试 |
| CAN/CAN FD | 中 | 车内 ECU 升级 |
| USB | 快 | 售后刷写工具 |
| 以太网 | 快 | 车载以太网 ECU |

## 6.3 常见坑

1. **擦除中断变砖**：升级断电导致 Flash 半擦半写 → 用 A/B 双区或"先擦后用"
2. **向量表没重映射**：中断全跑回 Bootloader → 设置 VTOR
3. **栈顶错误**：跳转前 MSR 设置新栈，避免用旧的
4. **看门狗**：擦写期间喂狗，防止升级中途复位
5. **Flash 对齐**：页擦除/写入需对齐到页边界

# 七、Bootloader 安全增强

| 安全机制 | 说明 |
|---|---|
| **安全启动** | 上电验证应用签名 |
| **刷写认证** | 进入编程模式需密钥认证（种子密钥算法） |
| **固件加密** | 固件密文存储，运行时解密 |
| **回滚保护** | 版本号单调递增 |
| **刷写计数** | 防刷写次数被篡改 |
| **防降级** | 新固件版本必须 ≥ 当前版本 |

### 种子密钥（Seed-Key）认证示例

```
① 上位机发 0x27 01（请求种子）
② Bootloader 返回随机种子 Seed
③ 上位机按算法计算 Key = f(Seed, 密钥)
④ 发送 0x27 02 + Key
⑤ Bootloader 验证通过才允许刷写
```

# 八、FOTA 发展趋势

## 8.1 升级策略演进

| 阶段 | 特点 |
|---|---|
| 单区就地升级 | 简单，风险高 |
| 双区 A/B 升级 | 安全回滚，主流方案 |
| 增量升级（Delta） | 只传输差异部分，流量大降 |
| 分层升级 | 应用/中间件/驱动分层独立升级 |
| 车云协同 | 大数据分析驱动定向升级 |

## 8.2 法规要求

- **UN R156**（SUMS）：软件更新管理体系，OTA 需经过认证
- 所有固件版本**可追溯、可验证**
- 升级失败需能**恢复到安全状态**

# 总结

Bootloader 与 FOTA 的知识主线：

> **Bootloader 原理（启动判定/跳转）→ Flash 布局（A/B 双区）→ 升级协议（UDS/CRC）→ 安全机制（签名/Seed-Key/回滚）→ FOTA 全流程（下载/验签/写入/激活）→ 法规合规（UN R156）**

**核心设计思想**：**可靠性优先**——升级任何时候都可能失败，因此必须保证"升不坏、可恢复、能回滚"。

> **一句话记住**：Bootloader 是 ECU 的"安全守门员"，FOTA 是"远程手术"——门必须永远开得了（防变砖），手术必须验明正身（安全认证），失败了还要能退回原样（双区回滚）。
